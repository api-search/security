{%- comment -%} WebMCP runtime — shared across every apis.io site. Included from _shared/_layouts/default.html INSIDE , because page-level scripts live in {{ content }} and run at parse time. If this moved below the content, every register() call on every page would hit an undefined global. WHY A RUNTIME AND NOT A PER-PAGE BLOCK. Until 2026-09 the homepage carried its own inline `navigator.modelContext.provideContext()` call. Two things went wrong with that and both are structural, not cosmetic: 1. The spec MOVED. The W3C Web Machine Learning CG draft of 2026-05-27 moved the getter from Navigator to Document (tools belong to a page, not to a browser) and the registration call from provideContext({tools}) to registerTool(tool). Chrome deprecated navigator.modelContext in Chrome 150; the origin trial runs Chrome 149-156. Our call was guarded by a `typeof … === 'function'` check, so when Chrome dropped the old surface the whole feature became a SILENT no-op — no error, no console warning, nothing in any diff. A draft spec will move again. One runtime means one place to follow it. 2. It could not be measured. We had no idea whether a modelContext-capable browser had ever loaded the page, let alone called a tool. Being early to a technology is only worth something if you can say what happened. SURFACE. Pages opt in: window.apisioWebMCP.register('home', [ {name, description, inputSchema, execute}, … ]); register() is idempotent per surface and safe to call before or after DOM ready. Tools accumulate across surfaces, so two components on one page cannot clobber each other (the legacy provideContext call replaces the WHOLE tool set, which is exactly the footgun this hides). RETURN SHAPE. The spec has execute() resolve to an MCP content array. Our tool bodies return plain JS objects because that is what the old Chrome build took. wrapExecute() normalizes: anything already shaped like {content:[…]} passes through untouched, everything else is JSON-stringified into a single text content part. Tool authors keep returning plain objects. MEASUREMENT. See /webmcp/beacon in cloudflare-worker/src/worker.js and the "WebMCP adoption" section of cloudflare-worker/QUERIES.md. Positives (a capable browser, a tool call) beacon at 100%; the no-capability case beacons at 1% so there is an unbiased denominator without paying for a write on every pageview. {%- endcomment -%}
